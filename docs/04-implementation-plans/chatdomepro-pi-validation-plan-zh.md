# ChatDomePro：Pi 验证与特色能力接入实施方案

## 1. 当前基线与实施目标

ChatDomePro 的目标是复用 Pi 的通用智能体运行能力，验证能否改善 ChatDome 在开放任务、连续执行和交互方面的表现，并保留主机安全领域的命令审批、受控执行、审计和巡检能力。

| 尚未完成 | 📋 依赖安装、应用代码、模型连接、对照测试、特色能力接入及部署 |

“Pi 能提高成功率”和“ChatDomePro 能降低模型用量”均为待验证假设。现有代码行数、仓库体积和功能数量不能作为这两个结论的证据。

本方案确定推荐实施顺序，不代表已经批准生产切换。阶段验收通过后才进入下一阶段，不以全部功能搬迁作为第一轮目标。

## 2. 路线与范围

### 2.1 推荐路线

ChatDomePro 先作为独立集成仓库，依赖固定版本的 Pi，通过公开扩展或软件开发工具包接入特色能力。只有复现了公开接口无法解决的问题，才创建 Pi 源码派生分支并维护补丁。

初期不导入 Pi 的整个仓库，不在安装后的依赖目录直接修改代码，也不复制 ChatDome 的完整智能体实现。原版 Pi 作为未修改的比较对象持续保留。

### 2.2 首轮交付范围

- 固定版本的原版 Pi 运行入口和 ChatDome 对照入口。
- 可重复的任务集、用量记录和结果报告。
- ChatDomePro 终端入口，支持流式输出、停止及运行中追加指令。
- 一条只读主机检查流程，以及一条经过审批、执行、审计的完整变更流程。
- Sentinel 巡检结果查询与分析；主动推送在后续阶段接入。

### 2.3 暂缓范围

- 独立网页控制台、多用户系统、多主机编排及通用插件市场。
- 自研模型适配层、自研通用任务循环、第二套会话压缩和会话分支系统。
- 一次性搬迁 ChatDome 全部记忆、历史会话、配置和 Telegram 管理菜单。
- 自动处置真实生产告警、自动切换现有 ChatDome 部署。

## 3. 模块职责与复用方式

| 模块 | 实施方式 | 唯一负责的状态 |
|---|---|---|
| Pi 运行模块 | 固定版本；优先使用公开接口 | 模型调用、智能体消息、会话分支、上下文压缩和运行事件 |
| ChatDomePro 应用模块 | TypeScript 编写；终端入口先行 | 用户请求关联、当前 Pi 会话映射、输入路由和界面投影；运行中消息队列交给 Pi |
| 主机执行模块 | 初期通过本地 Python 子进程复用选定 ChatDome 代码 | 命令预审、审批记录、执行状态、输出和审计 |
| 巡检模块 | 后续复用 Sentinel 的调度、规则和抑制机制 | 巡检结果及告警状态；不直接修改 Pi 的消息存储 |
| 记忆模块 | 后续提供受限的事实与证据查询 | 长期事实、证据来源和有效时间；不管理 Pi 的工作上下文 |
| 评测模块 | 对三种运行方式使用相同记录格式 | 用例、运行条件、结果、模型请求及用量 |

Pi 的消息历史与 ChatDomePro 的任务记录必须分开：一个用户任务可能对应多个 Pi 内部回合。使用 `task_id` 关联任务、`session_id` 关联会话、`tool_call_id` 关联工具调用、`operation_id` 关联主机操作；这些标识不得互相替代。

### 3.1 ChatDome 代码的接入顺序

以下路径相对于 ChatDome 核心仓库的 `controlplane/src/chatdome/`。

| 现有实现 | 处理方式 | 前置工作 |
|---|---|---|
| `executor/sandbox.py` | 优先复用执行、超时、输出截断和进程回收行为 | 检查日志、运行路径、命令包和审计依赖；所有运行路径指向实验目录 |
| `agent/tools.py` 中命令预审与审批事实 | 只提取必要规则和契约 | 当前文件耦合模型、会话及业务分发，不能直接将整个分发器嵌入 Pi |
| `agent/audit.py` | 复用审计事件及完整性校验思路 | 明确独立存储、序列化写入和原始输出保留策略 |
| `sentinel/pack_loader.py`、`packs/` | 先接入单一检查项 | 使用固定参数和脱敏测试数据验证输出 |
| `sentinel/scheduler.py` 等 | 后续接入定时巡检 | 当前依赖配置、日志、告警、执行器和运行路径，需要单独核查启动入口 |
| `agent/engram.py`、证据记忆 | 后续按查询接口接入 | 使用测试副本，定义过期事实与当前证据的优先级 |
| `agent/core.py`、`agent/session.py`、`context_compactor.py` | 保留作为旧产品和评测参照 | 不接入新运行时，避免双重管理消息、任务和压缩 |
| `llm/`、`telegram/bot.py`、安装菜单 | 不整体迁入首轮 | 模型层交给 Pi；远程交互与部署在验证通过后单独规划 |

首次复用使用固定提交的独立只读检出和独立 Python 环境，不从现有部署进程导入状态，不要求修改 ChatDome 工作区。验证通过后，将确实需要的代码作为有来源记录的模块或依赖管理；复制源码时保留原许可证、版权及适用的 NOTICE 文件，记录来源提交和后续同步方式。

### 4.2 环境约束

- Windows 用于编辑和一般终端验证；Linux 主机执行、进程取消与巡检验收在固定的 Linux 虚拟机或容器环境完成。两边比较必须使用相同目标环境。
- 按选定 Pi 发布版本的包元数据锁定 Node.js 运行版本、Pi 精确版本和完整依赖锁文件。核查时上游主分支标注包版本为 `0.85.1`、Node.js 要求为 `>=22.19.0`，不据此假定该版本已发布；安装阶段验证包可用性并记录实际版本。
- Python 版本应满足选定 ChatDome 基线，使用独立虚拟环境，固定实际安装版本和依赖。
- 明确排除个人全局技能、提示词、扩展和历史记忆的自动加载；记录最终加载清单。仅更改会话目录不能证明全局资源已隔离。
- 凭据只通过运行时配置提供，不进入代码、报告或模型工具可读取的测试目录。原始会话和调用记录留在忽略目录，提交报告前脱敏。
- 每次代码更新前执行 `git pull`；首次空远程没有分支时记录该状态，再进行初始提交。依赖升级独立提交并重跑固定回归集。

## 5. 分阶段实施

### 阶段 0：固定条件与用量记录

**依赖：** 测试模型的可用认证、可恢复的测试环境。未具备时仍可准备脱敏样例和离线测试，不启动付费模型任务。

- [ ] 建立最小 Node.js 工程、忽略规则和版本记录；不安装无关框架。
- [ ] 为 ChatDome、原版 Pi、ChatDomePro 预留独立工作区和会话目录。
- [ ] 选定一个主模型，记录精确模型标识、提供方、推理设置、输出上限和软件版本；提供方没有披露的模型修订标记为未知。
- [ ] 冻结首轮用例、成功标准和已知失败案例；在看到 Pi 结果前保存。
- [ ] 在模型请求层验证用量采集，覆盖主循环、压缩、审批分类、命令详情及重试；纯阶段进度事件不能替代模型用量记录。
- [ ] 配置每任务最大模型请求次数、最长时长和整批预算；没有明确预算不运行整批付费评测。

**验收：** 三个普通请求和一次人为触发的压缩调用均可关联到任务及实际用量；重复结束事件不重复记账；缺失用量被标为未知。版本与运行条件记录可由另一位开发者复现。

### 阶段 1：原版 Pi 与 ChatDome 对照

- [ ] 先选择一项用户实际遇到的失败案例，跑通两边入口和同一验收脚本。
- [ ] 执行第 7 节的首轮任务集，每个用例在每个比较对象上运行三次，交错顺序并重置测试环境。
- [ ] 保存各自默认提示词、工具清单和压缩设置，先进行产品默认行为比较。
- [ ] 对差异最大的案例进行受控复测：统一工具权限、目标环境、输出限制及任务约束，区分运行机制差异与工具配置差异。
- [ ] 记录失败原因：意图理解、证据不足、工具缺失、上下文丢失、执行失败、审批阻塞或模型拒绝等；不把全部失败归因于模型。

**验收：** 输出第一份对照报告。初步继续条件为至少两个预先记录的 ChatDome 失败案例在 Pi 上三次均完成，且发现可复现的改善机制。样本不足时标为探索结果，不声称统计显著。

**未通过：** 固定软件基线，先检查模型和工具配置；如 Pi 也不能解决目标问题，停止扩大融合范围，保留实验记录。此阶段不以网页或 Telegram 界面完成度作为验收指标。

### 阶段 2：ChatDomePro 最小完整流程

- [ ] 通过公开接口创建 Pi 会话；接入文本增量、工具开始/完成和错误事件，不另写智能体循环。
- [ ] 实现终端输入、立即停止、追加当前任务指令和排队后续任务；停止不通过模型分类。
- [ ] 启动本地 Python 桥接进程，先提供一个只读主机检查工具。
- [ ] 接入一条需要审批的测试变更命令，完成提出、确认、执行、结果回传和审计。
- [ ] 处理拒绝、超时、取消和子进程退出；将主机操作状态返回 Pi，禁止将未执行结果标记为成功。
- [ ] 禁用或替换可绕过审批的默认执行与写入路径，验证最终生效工具清单。

**验收：** 完成“读取状态 → 提出处置 → 用户批准 → 单次执行 → 展示证据”的流程；拒绝、超时和取消均不触发后续变更；断开桥接进程后不能继续执行。

### 阶段 3：巡检、证据与记忆

- [ ] 先读取固定的 Sentinel 历史结果，验证 Pi 能引用实际证据而不是编造检查结果。
- [ ] 接入单一真实巡检项、调度与抑制规则；使用测试对象，不接入现有生产告警流。
- [ ] 将主动告警作为独立输入事件排队；若当前任务正在审批，不直接改写其命令、审批绑定或会话文件。
- [ ] 增加带来源、时间和有效性信息的事实查询；只在用例证明必要时接入长期记忆写入。
- [ ] 在每个功能接入后重复阶段 1 的关键案例，观察是否引入过度追问、重复执行或用量增长。

**验收：** 告警可追溯到真实巡检输出；重复告警按既定规则抑制；旧事实不能覆盖新的主机证据；移除新增记忆模块时通用任务仍可运行。

### 阶段 4：完整对照与路线选择

- [ ] 执行 ChatDome、原版 Pi、ChatDomePro 三方对照，明确比较运行条件是否一致。
- [ ] 单独执行取消、重启、重复审批和输出截断回归；注入时机固定，不能只依赖自然出现的故障。
- [ ] 增加两个未用于调参的保留用例，检查是否只优化了已知样例。
- [ ] 记录实现一个新检查工具或变更审批规则的实际修改范围、耗时和测试结果，评估维护成本。
- [ ] 输出逐用例结果、失败轨迹、完整用量与未解决问题；作出继续集成、局部派生 Pi 或停止扩展的结论。

**验收：** 在具备相同任务约束和审批要求的比较中，ChatDomePro 保留基线验证得到的改善，执行约束回归全部通过，用量数据缺口已明确。失败和未知记录不得剔除。若只是输出更快、成功率没有改善，应明确报告这一结果。

### 阶段 5：受控试用，可选

阶段 4 通过后再增加 Telegram 入口、安装方式和服务运行配置。使用独立机器人、数据目录和测试主机；同一目标主机不得由新旧两个智能体同时自动执行变更。

开始生产试用前需另行明确部署对象、权限和回退步骤。首轮不迁移旧会话；如需导入长期事实，先导出可审阅副本，保留来源。停止试用时关闭 ChatDomePro 进程与调度，保留审计记录，现有 ChatDome 继续运行。

## 6. 审批与执行的必备契约

首轮采用本地子进程，通过标准输入输出传递逐行 JSON 消息；日志使用标准错误输出，不与协议消息混杂。协议只承载显式工具请求，不开放公共网络端口。每条消息包含协议版本、请求标识、操作类型和参数，限制消息长度和等待时间。

最小接口围绕准备操作、作出决定、查询状态和取消操作组织。模型只能提出操作和查询必要状态，批准或拒绝从可信用户输入通道进入；不能把一个可由模型自行调用的 `approve` 工具当作人工审批。

| 情形 | 必须实现的行为 |
|---|---|
| 创建操作 | 固定命令、目标主机、执行目录、相关环境、超时和输出规则；返回不可变操作标识及审批事实 |
| 用户批准 | 绑定当前身份、任务、会话和操作；执行器验证批准状态，不相信提示词中的授权声明 |
| 修改命令或目标 | 旧批准失效，重新创建操作；命令中变量、脚本内容和目标路径变化也需纳入验证 |
| 重复点击或请求重传 | 同一操作不重复启动，返回现有状态；不是仅在界面隐藏按钮 |
| 等待时追加新要求 | 涉及当前操作的改向先撤销待审批操作，再将新要求交给 Pi；排队后续任务不修改当前批准 |
| 停止 | 向 Pi 和执行器传播取消，处理子进程组并等待终态；已产生的系统副作用不能承诺撤销 |
| 进程重启 | 待审批操作默认失效；执行中操作按已持久化状态核查，结果未知时不自动重放 |
| 崩溃发生在命令启动附近 | 记录结果未知并核对主机状态；不承诺仅凭请求标识就能实现跨崩溃的严格单次执行 |
| 输出超限 | 返回截断标记和证据引用，可按需读取后续片段，不能把截断内容当作完整证据 |
| 默认 Pi 工具 | 主机变更必须进入同一个受控执行入口；直接 shell、文件编辑、脚本或扩展绕过属于验收失败 |

测试环境隔离不能仅依赖工具名称或提示词。Pi 默认继承启动进程权限，ChatDome 的执行封装也不等于操作系统隔离；对不可信命令的真实限制由测试主机、容器或操作系统权限落实。第一轮不加载未知第三方扩展。

审批状态由执行模块持久化，Pi 只接收其投影。具体如何在 Pi 等待工具期间处理改向、取消和重启，需要在阶段 2 实测；不能因公开接口存在就视为已经兼容。

## 7. 首轮评测用例

用例输入、初始状态和验收断言在运行前冻结；表中场景需替换为用户提供的实际失败案例与脱敏数据。标识只是评测编号。

| 编号 | 场景 | 成功标准 |
|---|---|---|
| E01 | 从多份日志和配置定位服务异常 | 给出正确原因和对应证据，区分事实与待验证假设 |
| E02 | 常用检查命令不存在 | 选择环境中可用的替代方法，不循环重试同一失败命令 |
| E03 | 根据测试项目资料修改配置并验证 | 产生正确文件改动，通过预设验证，不修改范围外文件 |
| E04 | 开放任务的多步推进 | 完成预定义终态，遇到可自行检查的信息缺口继续取证 |
| E05 | 执行中追加仅检查、不修改的要求 | 到达改向处理点后不再启动新变更，报告已经发生的动作 |
| E06 | 审批期询问风险后拒绝 | 回答与当前操作对应，拒绝后执行次数为零 |
| E07 | 批准操作、重复确认并查询结果 | 操作只启动一次，状态和审计一致 |
| E08 | 长日志触发压缩后追问早期事实 | 保留或检索正确证据，不混淆时间和对象 |
| E09 | 连续两项不同任务 | 既不擅自续做旧任务，也能理解明确的继续请求 |
| E10 | 工具长时间运行时停止 | 执行器与 Pi 均停止继续推进，测试子进程按约束回收 |
| E11 | 审批或执行期间重启 | 过期批准不能执行，状态未知的操作不自动重放 |
| E12 | Sentinel 重复告警与后续追问 | 抑制符合预设规则，分析引用告警对应的主机证据 |

原版 Pi 不具备与 ChatDome 相同的审批或巡检时，相应案例在默认比较中标为不适用，不当作通用能力失败，也不计入相同任务的 Token 节省结论。阶段 2 后，以拥有同等执行限制的 Pi 集成基线与 ChatDomePro 比较；报告保留原版与集成版的区别。

首轮共同适用案例至少重复三次。三方全部适用时，12 个案例乘以三次再乘以三个对象，最多形成 108 次运行；不适用项目单独列出。每次使用独立会话，长对话用例除外；恢复测试只恢复本次案例指定的状态。

报告同时给出逐例成功率、正确完成所需人工补充次数、无效工具调用、任务用时和失败原因。首轮样本用于工程选择，不能替代长期稳定性测试。

## 8. Token 与费用评测

Token 指模型输入、输出的文本计量单位。以整个任务为归属范围，统计所有已知被计费的模型请求，不能只统计最终回答或主循环。

### 8.1 必须覆盖的调用

- 正常推理、工具循环和模型侧推理用量。
- 自动及手动上下文压缩、分支摘要。
- 审批期自然语言分类和按需命令详情分析。
- 失败、取消、重试及扩展内部额外模型调用。
- 巡检触发的模型分析；纯本地规则检查记为无模型调用。

当前 ChatDome 的 `agent/context_compactor.py` 存在独立模型调用及重试，所检查路径未见写入现有 `TokenTracker`。评测从模型请求层核对覆盖面，在独立评测检出中增加必要观测，不修改当前产品工作区。现有累计显示不能直接视为完整账单。

### 8.2 每次请求的记录

至少包含运行标识、任务标识、请求标识、尝试序号、提供方与模型、调用用途、起止时间、完成状态、输入与输出 Token、可用时的缓存读写与推理用量、来源及原始用量字段。

缺失字段记录为未知，不能当零。保存提供方原始计数，按提供方定义归一化，防止将已计入输入的缓存用量或已计入输出的推理用量重复相加。流式累计快照只能结算一次；终止请求没有最终用量时标为缺失，并尽可能与提供方侧记录核对。

任务总用量为归一化后的全部请求用量之和。若用量未完整覆盖，不发布该任务的确定节省百分比。所有失败任务的已知成本仍计入整批成本。

### 8.3 两类比较分开报告

1. 默认产品比较：各自默认提示词、工具和压缩策略保持不变，记录差异；回答开箱行为是否更好。
2. 受控比较：统一模型、推理设置、任务成功标准、环境、权限、工具结果预算与停止预算；保留必要的运行时差异并记录。需要时单独改变压缩策略，观察用量与证据保留之间的取舍。

冷缓存和缓存复用场景分别测量；提供方无法控制缓存时记录为不可控并交错运行，不声称已完成严格冷缓存比较。账号订阅授权不一定有按请求账单，此时仅报告用量，不能从推测单价生成实际费用。

单任务节省比例只在两边均满足同一成功标准且用量完整时计算。还要报告整批成本、成功率和每成功任务成本，避免通过提前停止、少做任务或排除失败来制造节省。提供方有计费价格时记录价格来源及日期，区分估算费用与实际账单。

## 9. 测试与继续条件

| 阶段 | 验证方式 | 阻止继续的情况 |
|---|---|---|
| 0 | 请求用量与任务关联检查、重复事件检查 | 模型版本不明、关键调用漏记、缺失用量被当零 |
| 1 | 固定任务的重复对照、失败轨迹审阅 | 只有主观体验变化，找不到可复现的目标能力改善 |
| 2 | 真实桥接子进程、审批重复操作、取消及故障注入测试 | 任何绕过审批、重复执行、拒绝后执行或假成功 |
| 3 | 固定时间与事件输入的巡检回归、记忆来源检查 | 旧事实覆盖新证据，告警干扰当前批准或造成重复任务 |
| 4 | 完整回归及未用于调参的用例 | 特色能力接入后主要收益消失，维护成本持续转移到进程协调 |
| 5 | 独立测试部署、退出和回退演练 | 无法隔离旧部署，无法确定新进程和调度已停止 |

契约和故障注入测试优先使用本地确定性测试，不消耗模型调用。真实模型只用于能力和端到端任务验证。测试穿过公开工具与执行接口，不能仅通过模拟内部方法来证明审批和进程取消正确。

## 10. 何时派生 Pi 源码

只有出现以下完整证据时才维护 Pi 补丁：固定版本可复现的问题、公开接口与扩展无法解决的原因、最小改动范围、回归用例和上游同步策略。单纯更换名称、提示词、工具或界面文案不要求派生底层源码。

派生后配置独立上游远程并保留来源历史，补丁单独提交，不把本项目业务文件散布到 Pi 各底层包。每次升级先验证未修改 Pi 基线，再运行 ChatDomePro 回归；不把 ChatDome 的全部历史规则直接加入 Pi 系统提示词。

## 11. 首批工作项与交付物

按依赖顺序开始，前五项通过后再扩大功能：

1. 固定 Pi、Node.js、Python 和 ChatDome 参考提交，建立独立运行目录。
2. 将一个实际失败案例写成可判定的任务与测试环境。
3. 建立主循环及压缩请求的完整用量记录。
4. 完成 ChatDome 与原版 Pi 的三次重复对照并分析差异。

每个阶段交付可运行入口、相关测试、版本记录和一份简明报告。报告包含已完成、失败、未测及下一阶段依据；不将本方案中的待办直接标记为实现状态。
